设计一款超越传统 ChatBI 的产品，核心在于实现从**“被动的数据查询可视化工具”**向**“主动的商业决策与执行引擎（Agentic Decision Intelligence）”**的跨越。

传统的 ChatBI 解决了“Text-to-SQL/Chart”的问题，但依然依赖人去解读数据、制定策略并跨系统执行。真正具备 Agentic 能力的下一代产品，应该是一个企业级的认知引擎，能够完成“感知数据 -> 洞察异常 -> 制定策略 -> 联动上下游系统自主执行 -> 效果追踪”的业务闭环。

以下是主导设计这样一套 Agentic BI 产品的详细规划：

### 一、 产品愿景与核心差异化

我们的目标不是做一个更好的数据问答机器人，而是打造一个**企业智能体中枢**。

* **传统 ChatBI：** “帮我看看上个月华东区的销售额和利润率。”（输出图表）
* **Agentic BI：** “华南区库存周转率为何异常？如何解决？”（不仅输出归因分析，还自动生成补货单或促销策略，并询问：“是否确认将此促销策略同步至 CRM 和 ERP 系统执行？”）

**核心特性设计：**
1.  **主动感知与异动洞察 (Proactive Intelligence)：** 不等用户问，系统后台实时监控指标池，结合时序预测模型，发现异常主动推送告警与归因分析。
2.  **多智能体协同 (Multi-Agent Collaboration)：** 拆分复杂任务。例如：数据分析 Agent 负责取数算数，业务推理 Agent 负责结合行业 Know-how 找原因，执行 Agent 负责调用外部系统 API。
3.  **上下游系统联动 (Action-Oriented)：** 具备极强的 Tool Use 能力，可以直接将决策转化为业务系统的操作（如：调整供应链系统的预测参数、在营销平台触发一波发券动作）。
4.  **人机协同与反馈学习 (HITL & Memory)：** 涉及资金和高风险决策时，通过 Human-in-the-loop 进行审批。系统会记住用户的偏好、历史决策的ROI，持续自我进化。

### 二、 整体架构设计 (Agentic BI Architecture)



为了支撑上述业务闭环，架构需要分为五个核心层：

#### 1. 基础设施与数据层 (Data Foundation)
* **统一数据湖/数仓：** 汇聚全域业务数据。
* **指标管理中心 (Metrics Store)：** **这是 ChatBI 成功的基石。** LLM 极容易在复杂的 SQL 联表中产生幻觉。必须将业务逻辑下沉到指标字典，LLM 的核心任务是识别意图并调用计算引擎的 API（如 Cube 查询），而非直接拼接复杂的底层 SQL。

#### 2. 语义与知识层 (Semantic & Knowledge Layer)
* **业务知识图谱 (Knowledge Graph)：** 映射企业实体关系（如“商品”-“类目”-“供应商”），帮助大模型理解企业专属术语。
* **RAG 向量检索库：** 存储过往的分析报告、沉淀的 SOP（标准作业程序）、决策日志，为 Agent 提供上下文。

#### 3. Agentic 认知与编排层 (Cognitive Engine)
这是整个产品的大脑，采用多智能体协作架构：
* **Router/意图识别 Agent：** 接收输入，判断是简单查数、深度诊断、还是执行指令。
* **规划器 (Planner)：** 采用 ReAct 或 Plan-and-Solve 模式，将大目标拆解。例如：“提升A产品销量” -> 拆解为查库存、查竞品、定策略三步。
* **专家 Agent 组：**
    * *Data Agent：* 负责 Text-to-SQL / Text-to-Metrics API，处理图表渲染逻辑。
    * *Analysis Agent：* 负责方差分析、归因分析（如利用波士顿矩阵、杜邦分析法生成洞察）。
    * *Action Agent：* 负责将分析结果转化为行动 payload。

#### 4. 执行与网关联动层 (Execution & Action Layer)
* **API Gateway & RPA 集成：** 提供标准的鉴权和接口封装，允许 Agent 跨系统调用 ERP、CRM 或供应链平台。
* **沙盒模拟 (Simulation Environment)：** 在正式下发指令前，调用预测模型进行沙盒推演（例如预测调价后的收益变化）。
* **审批流引擎 (Approval Engine)：** 对接钉钉/企微等，实现关键动作的人工确认。

#### 5. 交互层 (Interaction Layer)
* **动态 UI (Generative UI)：** 交互不仅仅是对话框。系统应根据当前任务，动态渲染表格、交互式看板、甚至是一个微型的审批表单。

### 三、 关键技术规划

#### 1. 大模型选型与部署
* **混合模型策略：** * **基座推理模型：** 采用顶级的闭源模型（GPT-4o, Claude 3.5 Sonnet）或领先的开源大模型（DeepSeek-V3/R1, Llama 3）负责复杂的逻辑链推理、Plan 拆解和工具调用。
    * **垂类专用模型：** 针对 Text-to-SQL 环节，可以使用经过微调的小模型（如基于 Qwen 或 CodeLlama 针对企业 Schema 微调），以提高准确率和响应速度，并保护数据隐私。

#### 2. 解决 Text-to-SQL 的准确率痛点
传统的 ChatBI 痛在准确率无法突破 80%。解决方案：
* **Schema 增强与剪枝：** 在 Prompt 中不塞入全量库表，而是通过 RAG 先检索相关的 Schema 和注释。
* **Self-Correction 闭环：** Agent 生成 SQL 后，必须内置一个验证节点，先在数据库执行 `EXPLAIN` 或加上 `LIMIT 1` 试跑，如果报错，自动将报错信息喂给模型进行修正（Reflection）。
* **基于语义层的 Text-to-DSL：** 尽量绕过底层明细表 SQL，让大模型生成特定 BI 引擎（如 Apache Superset, Metabase）的 DSL 或 API 请求。

#### 3. Agentic 决策闭环的实现
为了让系统能与上下游联动，必须建立标准化的 **Tool/Function Calling 注册表**。
* **入参：** Agent 从数据洞察中提取参数（如：异常 SKU 列表、降价幅度）。
* **出参：** 调用 ERP 的 `update_price_strategy` API。
* **状态机维护：** 采用 LangGraph 或类似的状态机框架，持久化记录任务流转状态，确保长生命周期的异步任务（如等待领导审批）不会中断。

#### 4. 安全与权限控制 (Security & Governance)
* **数据行/列级权限：** Agent 生成的查询必须附带当前用户的权限上下文，强制增加 `WHERE user_id = xxx` 等条件过滤。
* **操作审计：** 所有 Action Agent 对外部系统的写入操作，必须记录完整的思考过程（Chain of Thought）、调用的 API 及其快照，确保可追溯。

### 四、 产品落地路径 (Roadmap)

切忌一步到位做大而全的系统，建议分三期演进：

* **Phase 1：增强型数据副驾 (Copilot)**
    * 打通数据源，建立健壮的指标字典。
    * 实现高准确率的意图识别与数据提取，支持多轮对话追问和动态图表生成。
* **Phase 2：主动诊断与洞察 (Analyst)**
    * 引入监控与归因算法。
    * 系统具备“找问题”的能力，不仅呈现数据，还能生成结构化的业务诊断报告。
* **Phase 3：自主执行智能体 (Agent)**
    * 打通 CRM、供应链等上下游系统的 API 网关。
    * 实现核心业务场景（如自动补货预警与下发、异常客诉自动分发与跟进）的全自动闭环与人机协作审批。

将 BI 升级为业务系统的中枢，不仅是对数据价值的深度挖掘，更是向企业智能化运营迈出的关键一步。
